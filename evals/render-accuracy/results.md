# Indic render accuracy

Measured 2026-11-09T09:58:16.901Z. Generated by `evals/render-accuracy/run.ts`; raw data (every OCR reading) in `results.json`.

Question: when a reference is rendered and then read back by OCR, does it spell the requested phrase exactly?

## Arms

- **shaped**: the Sulekh provider render (HarfBuzz 15.0.0 shaping), the script's kalam-style font, size medium.
- **unshaped baseline**: the same font and layout, but each code point's nominal glyph is drawn left to right with no shaping. It reproduces the failure class (broken conjuncts, matras in logical instead of visual order, unjoined Arabic letters drawn left to right). It is a deterministic baseline, **not an image model**.
- **shaped-plain / unshaped-plain**: the same two arms with the script's plainest font, as an OCR control for calligraphic fonts. For Urdu the catalog has only Noto Nastaliq Urdu, so the control is Noto Naskh Arabic (OFL), fetched into the work cache for this measurement and not shipped with the app.

Raster: resvg, white background, 1500×1000. OCR: tesseract.js 7.0.0 (SIMD LSTM core; see tesseract-worker.cjs), OEM LSTM_ONLY, tessdata 4.0.0_best_int, PSM 7 (single line) or 6 (two lines). Score: exact NFC match after whitespace normalisation, plus character error rate (CER). The secondary "exact ignoring joiners" count also deletes U+200C/U+200D from both strings: Tesseract appends an invisible ZWNJ after word-final viramas (e.g. "வணக்கம்\u200c"), which fails the strict match without any visible difference.

## Notes on OCR limits (read before quoting numbers)

- OCR is a proxy for "a reader sees the right text", and a weak one for calligraphic Indic fonts. Every shaped render passed `validateReference` before OCR (no .notdef, no dotted circle, NFC text identical to the request), so a miss in a shaped arm is an OCR misreading of a correct render, not a wrong render.
- Calligraphic fonts (Kalam, Baloo Paaji 2, Meera Inimai, Galada, Noto Nastaliq) are far from Tesseract's training fonts. Compare the two per-script tables to see how much of a miss is font style.
- Tesseract's `urd` model reads Naskh-style print far better than Nastaliq; the Nastaliq rows mostly measure that limit. The unshaped Urdu baseline draws isolated letters left to right, which `urd` mostly reads as nothing.
- The unshaped baseline is sometimes read *correctly*: Tesseract's language model can repair visible halants or a matra drawn after its consonant into the intended spelling. That makes the baseline numbers an upper bound on how readable naive rendering is, not a measure of how it looks to a person.
- Exact match is strict: one wrong code point (nukta, anusvara vs chandrabindu, a dropped space) fails the phrase. CER shows how close the reading was.
- The phrases were fixed before the first run and not changed afterwards. No OCR post-correction beyond NFC, whitespace and (secondary metric only) joiner removal.
- Every SVG and PNG is kept in `../.chaupal-work/render-accuracy`.
